## Goals / Non-Goals

**Goals:**

- Map is a mode like the other three: same tab, same reading of the file, same selection, same memory, and no new way to select a record.
- The pure parts — coordinate reading, the places table, projection, tile planning, clustering, label collision, years range, hit testing — are plain functions with tests, in the layer `src/desk/` already uses for such things; the board is a thin DOM shell over them.
- The plugin's network promise gets no exception except one the reader switches on and can read, and the first request is the reader's.
- Desktop and phone from the first commit.

**Non-Goals:**

- A reusable map engine. The board draws what this view needs; nothing else is promised.
- Any change to the language service, the validator or the codemirror package.
- Persisting the years range, the search text or the panel (kept in the tab's board, not saved, as the list keeps its filter).

## Decisions

### D1. The model: `FileMap`, built from the index and the places table

A new pure module `src/desk/fileMap.ts` builds, once per `(GenealogyIndex, PlacesTable)` pair (a `WeakMap` per index, then per table object, as `fileTimelineOf` does at `fileTimeline.ts:502-512`), a `FileMap`:

- `places`: one `MapPlace { key, name, coordinates?, events }` per distinct place. `key = placeKey(text)` (trim, collapse white space, NFC, `toLowerCase`); `name` is the first spelling met in file order. Coordinates: the first valid `MAP` among the place's events in file order, else the table's, else none (priority per the user's decision 1).
- `events`: `MapEvent { record, kind, tag, label, year?, span? , order }` for every event with a place: the events of `person.events` (`Person.events`, `types.ts:181`) and of `family.events` (`types.ts:151`), each once (a marriage is the family's, not one per spouse). `kind` is `kindOf(tag)`, which `fileTimeline.ts:117` exports for this (it is private now; exporting is the only change to that file). `year` is the earlier of `date.year` and `date.end`, `span` is `[min, max]` of the two where `end` exists, so that a period and a `BET … AND …` overlap a range alike. The model does **not** use `FileTimeline.marks`, because marks exist only for dated events (`markOf`, `fileTimeline.ts:134`) and an undated event must still count and sit at its place.
- `scope(branch)`: the set of events whose record is a person in `fileTimelineOf(index).branch(focus, up, down)` (`fileTimeline.ts:64`), or a family with a spouse in it; the whole file when there is no focus. `LARGE_FILE`/`initialFocus` (`fileTimeline.ts:74,493`) are **not** applied: a map aggregates, so it opens on the whole file whatever its size.
- `route(record)`: the dated events of a person (own plus the families they are a spouse in, `Person.unions[].events`, `types.ts:169`) or of a family, with coordinates, in the range, ordered by `(year, order)`, consecutive same-place events merged, each stop carrying its order numbers.
- `mapSelection(index, xref)`: the xref where it is a person or family, else null (the pure twin of `listSelection`).

`PersonEvent` gains `coordinates?: { latitude, longitude }` read in `eventsOf` by a new `readCoordinates(place)` beside it in `src/genealogy/` (`childOf(place, "MAP")` → `LATI`/`LONG` → `^([NSEW])\s*(\d+(?:\.\d+)?)$` and a range check; a half pair or an out-of-range value gives `undefined`). `eventsOf` today calls `childOf(child, "PLAC")` twice (`events.ts:23-25`); it binds it once. Only the model reads syntax-tree symbols, so the board never touches `DocumentSymbol`.

*Alternative considered:* read `MAP` in `fileMap.ts` from the symbols. Rejected: the model is the one place that reads `PLAC` (`genealogy-read-model` says events are reported from a named set of structures), and `api.ts` or a later card could want the coordinates.

### D2. Place identity

Two spellings are one place when `placeKey` agrees: case-folded and white-space-collapsed, not accent-folded and not comma-normalised (`Paris,France` and `Paris, France` differ; the table is where a reader fixes that). Recommended by the planner, to confirm: this is the smallest rule that cannot merge two places the file keeps apart; a looser one (accent-folding) would merge `Orléans` and `Orleans`, which may be two towns in a historical file. The search folds accents (D10) because finding needs it; identity must not.

### D3. The places table: format, location, lifecycle

`<name>.places.md` in the `.ged`'s folder (`curie.ged` → `curie.places.md`; `.gedcom` the same). A plain note, so the reader edits it in Obsidian's own editor, with the table editor in Live Preview. Format:

```
| Place | Latitude | Longitude |
| --- | --- | --- |
| Warsaw, Congress Poland | 52.2297 | 21.0122 |
| Paris, France | 48.8566 | 2.3522 |
| Santiago, Chile | S33.4489 | W70.6693 |
| Stockholm, Sweden |  |  |
```

Rules are in the spec (`genealogy-map`, *The places table is a note next to the file*): first table of the note; header and delimiter skipped by position (so `Место | Широта | Долгота` works); `\|` escapes a bar; decimal point or comma; optional hemisphere letter before or after, never with a sign; out-of-range or empty gives no coordinates; first row of a repeated place wins; anything else in the note is ignored. Pure parser `parsePlacesTable(text): PlacesTable` never throws and returns `{ rows: Map<key, Coordinates | null>, names }`; `placesTablePath(gedPath)`; `placesTableText(places, collator, note)` builds the created note.

*Why a note and not JSON or a sidecar:* the reader asked for hand-editable; a Markdown table is editable in Obsidian with no tooling, is searchable, syncs and is diffable. *Why positional header:* the file is created in English but a reader of another language will rewrite the header.

**Lifecycle (hosted by `main.ts` and the tab, not by the pure code).** The tab asks the host for the table text when it enters Map mode and whenever the host reports that path changed (`vault.on("modify" | "create" | "delete" | "rename")` registered once in `main.ts` next to the existing rename listener at `:252`, dispatching to the tabs whose table path matches). All of `vault.getAbstractFileByPath`, `cachedRead`, `create`, `on(...)`, `fileManager.renameFile` and `workspace.getLeaf(...).openFile` exist well below 1.8.7, so no floor is touched. Reading is cheap and debounced to one read per change.

**Rename (recommended by the planner, to confirm).** When a `.ged` is renamed or moved (the existing rename event) and `<old>.places.md` exists and `<new>.places.md` does not, the plugin renames the table with `fileManager.renameFile` (which updates links to it) and gives a notice. Otherwise both stay. *Why:* a table is useless once separated from its file, and a silent orphan makes a map "lose" its coordinates with no visible cause. *Cost:* the plugin renames a note the reader owns — one the reader created by an explicit action, named after the file, and the notice says so. *If not confirmed:* the table is found by name only, a renamed `.ged` loses it, and the empty-state message names the path the table is expected at.

**Create (decision 8).** `Create the places table`: the host calls `vault.create(path, text)`; on "already exists" (a race or a stale view) it opens the existing note and creates nothing. The text is a one-line note in the language of the plugin (`map.table.note`) above the table; headers always English. Rows: the distinct places the file has **no `MAP` for** (recommended by the planner, to confirm — decision 8 says "the file's distinct place names"; rows for places that already have a `MAP` would never be read, since the file wins, and would only make the table longer to edit), named as first written, sorted with the plugin language's collator. When the note exists and no place has coordinates, the button reads *Open the places table*. The creation writes that one note and nothing else.

*Appending the missing places to an existing table* (a button "Add the N places that have no row") is **not** in this change; the counter opens the list and the reader adds rows by hand, as decision 1 says. See Open questions.

### D4. The outline: Natural Earth, packed

**Source (recommended by the planner, to confirm after one look at the result):** Natural Earth `ne_110m_land` (public domain; naturalearthdata.com), land polygons only: no borders, which would mislead for historical files and are out of scope by decision 9, no lakes, no labels.

**Packing.** A generator script `scripts/outline.mjs` (outside `src/`, so Node is allowed, as for `harness/build.mjs`) takes the GeoJSON path as an argument, drops rings under a small area, simplifies to a 0.1° tolerance, quantises longitude and latitude to 0.05° into integers, delta-encodes each ring, writes the deltas as zigzag varints, and base64-encodes the bytes into a generated module `src/desk/mapOutlineData.ts` (one exported string, committed). Expected size: 110 m land has a few thousand vertices; at 2–3 bytes a vertex that is 10–25 KB raw, 15–35 KB base64 — the budget is 300 KB (decision 3) and the spec requires ≤ 300 KB. `decodeOutline(data): Ring[]` (pure; `atob` exists on mobile) yields rings in degrees; `outlinePath(rings)` projects them to one SVG path in world units `[0, 256]²` (Web Mercator, latitude clamped to ±85.05113°), built once and reused for every draw. The source file is not committed; the script and its command line are documented in the README *Development* section, with the licence note under *Credits*: "Land outline from Natural Earth (public domain)". The generated module carries no comment; the licence is in the README, where a reader looks for it.

*If 110 m is too coarse once seen at city zoom:* the same script runs on `ne_50m_land` at 0.02° tolerance; the budget allows it (50 m land, simplified, is ~100–200 KB). The task makes the choice by a screenshot, and a unit test pins the generated size under the budget either way. *Alternative rejected:* an SVG world map asset (large, hand-drawn, unclear licence) and any runtime download (violates decision 2).

### D5. Projection, view and zoom

Web Mercator in a pure `src/desk/mapProjection.ts`: `project(lat, lon) → [wx, wy]` in `[0,1]²`, `unproject`, clamping latitude to ±85.05113°. The **view** is `{ x, y, k }` in the same shape the graph uses (a CSS-like translate and scale), where the world is `256·k` pixels wide, `k = 2^zoom`. This is deliberate: `GraphInput` (drag, pinch, wheel; `graphInput.ts:27-170`) is written against `{x, y, k}` and a host that applies it, so the map reuses it by making the zoom limits the host's: `GraphInputHost` gains `limits(): { min: number; max: number }` in place of the import of `ZOOM` (`graphInput.ts:2,145`). The graph answers with its `ZOOM`, so its behaviour does not change; a test pins that.

What is **saved** (in `DeskState.map`, `MapState = BranchScope & { view?: { lat, lon, zoom } }`) is the centre and zoom, not the pixel transform: a tab restored in a different width shows the same place, which `{x,y,k}` would not. It is rounded (lat/lon to 4 decimals, zoom to 2) and read defensively as `readGraphState` does (`fileGraphView.ts:47`).

Limits: the minimum zoom is the one at which the world just fits the tab (never smaller); the maximum is 12 without tiles and 18 with them (the outline at street scale is meaningless; a view saved above the limit is clamped on read). The centre is clamped so some of the world is always in the tab. No world wrap (non-goal): points at ±180° sit at the two ends of the one world. *Alternative:* wrap with duplicated marks — doubles drawing and selection ambiguities for little gain in a genealogy tool.

### D6. Drawing: an SVG shell, screen-space marks, virtualised

One `<svg>` per board with three layers: the **base** (the outline as one `<path>` inside a `<g>` carrying the world transform, `vector-effect: non-scaling-stroke`), the **tiles** (an HTML layer under the SVG, see D7), and the **marks** (points, clusters, lines, arrows, labels) in screen space, positioned by projecting each place through the current view. Marks stay a constant size at any zoom, which a transformed group cannot give without per-mark counter-scaling.

Only what is in view and in a margin is projected and drawn. Clusters are made from that set (D9), so the document holds a bounded number of marks (a few hundred) whether the file has fifty places or five thousand; `PlaceGrid` (`src/desk/mapHits.ts`, pure) is a spatial hash over world coordinates built once per model, answering "the places in this rectangle" without scanning all, and also the pointer hit test. Marks are pooled by key and their `transform` updated during a drag, rather than rebuilt; the label pass runs when the view settles (a frame after the last change) and not on every pointer move.

*Why not canvas:* the timeline is SVG with a virtualised window, the Playwright specs query elements, and accessibility names and focus rings are free on elements. At a few hundred marks SVG is fast enough; canvas would be the next step if a measurement says otherwise (task 7.x measures, as the timeline's specs do).

**Glide.** Not the CSS transition of the graph (`graphCanvas.ts:619-680`), because that scales one element and the marks are screen-space. A small `glide` interpolates the view in log-zoom and screen centre with an ease-out over `GLIDE_MS` using `requestAnimationFrame`, re-projecting the pooled marks each frame; it jumps where `prefersReducedMotion(doc)` (`dom.ts:132`) or where the move is longer than `GLIDE_REACH` screens (the same rule as the graph, `graphCanvas.ts:639-645`); a drag, the wheel or a key takes over from the point reached. `GLIDE_MS` and `GLIDE_REACH` are exported from `graphCanvas.ts` (they are module constants today) so both boards share them. The interpolation is a pure function in `mapProjection.ts`.

### D7. Tiles: an image layer, off by default, never in the way

Settings: `mapTiles: boolean` (off), `tileUrl: string` (empty), `tileAttribution: string` (empty) — new keys in `GedcomSettings` (`settingsData.ts:9-18`), `DEFAULT_SETTINGS`, `parseSettings` and `changedSetting`. A text value is stored **as typed** (capped at 2048 characters) and judged at use: `changedSetting` accepts a value only when `parseSettings` returns it unchanged (`settingsData.ts:52-62`), so trimming or validating on save would reject every half-typed address. `tileTemplate(settings): string | null` (pure, in `src/desk/mapProjection.ts` or `mapTiles.ts`) returns the trimmed address when it begins with `https://` (case-insensitive), holds `{z}`, `{x}` and `{y}`, and `new URL(...)` accepts it with `0/0/0` put in; else null. A non-empty address that fails shows *The tile server address is not valid* in the settings row's description area and on the map's status; nothing is requested.

`planTiles(view, size, ring, maxZoom)` (pure) returns the `{z, x, y}` keys covering the view plus a ring, at `z = clamp(round(zoom))`, with their world rectangles; `x` wraps are not needed (no wrap), `y` out of range is dropped. The tile layer is a `<div>` under the SVG with the same translate/scale as the base; each tile an `<img>` (`crossorigin` unset, `referrerpolicy="no-referrer"`, `decoding="async"`, `alt=""`) sized in world units. `<img>` rather than SVG `<image>` because error and load events are dependable on every engine the app runs. Requests start only when the view has settled (150 ms without change) so a drag or a glide does not queue a fetch per frame; tiles that leave the planned set have their `src` cleared. At most the viewport's tiles plus one ring are alive (≤ ~40 on a large desktop, ~20 on a phone).

The outline stays above the tiles as a line without fill (`.is-tiles` on the root). `TileFailures` (pure, clock injected): a failed key is not retried for 60 s while it stays planned; three failures within ten seconds with no success set the status *Tiles could not be loaded*; a success clears it. A tile error never throws and never blocks anything: marks are drawn from the model before any tile is asked for, and the tile layer shares no promise with them.

**Privacy statement** (README *Privacy*, `README.md:227-239`, and the settings description): "With **Load map tiles from the web** on, the map asks the tile server you name for the images of the part of the world in view. That server learns the tile numbers — which say what part of the world you are looking at — and your IP address, as any website does. No place name, person or date is sent, and nothing is sent while the setting is off or the address is empty." The text *It makes no network request until you ask it to* stays true; the "one thing you can ask for" becomes two. `http://` is refused as it is for images.

**Attribution** (recommended by the planner, to confirm): the map must show attribution when tiles are on, and the plugin cannot know what a reader's server requires, so the reader supplies it in **Tile attribution**; empty, the map shows the server's host name, so attribution is never absent. It is plain text set with `setText`, never taken from the server and never HTML. Known limit: some public servers (for example `tile.openstreetmap.org`) require an identifying `Referer` and `User-Agent` that a desktop app cannot always supply; a reader who hits that uses a provider that allows it. The README says which setting to look at and ships no server.

### D8. Settings rows

`settingDefinitions()` (`settingDefinitions.ts:23`) gains, after `remoteImages`, three rows: a toggle (`mapTiles`), a text control (`tileUrl`, placeholder `https://tiles.example/{z}/{x}/{y}.png` — a reserved `.example` host, a hint and never a default) and a text control (`tileAttribution`). `GedcomSettingDefinition.control` widens to include `SettingTextControl<SettingKey>`; `settings.ts`'s legacy `render` (`:51-74`) gets a `text` branch with `Setting.addText` (long-standing API) so an app older than 1.13 shows the rows too. The rows are always shown; the address and attribution descriptions say "applies while tiles are loaded". That declines `visible`/`update()` (1.13.0) a second time, so **CLAUDE.md's table gets a row** in this change (the existing second row concerns *Open the side panels when selecting*; this is a new one, same API, same floor), and the lint rule `obsidianmd/no-unsupported-api` must stay quiet. `minAppVersion` stays 1.8.7; the change touches no `manifest.json` and no `versions.json`.

### D9. Points, clusters, labels, route (pure modules)

- **Size and colour.** `radius(n) = min(22, 5 + 1.7·√(n − 1))` px; the hit target is `max(radius, 22)` px (44 px, decision 7). Colour: the kind's class (`is-birth`, `is-death`, `is-marriage`, `is-other`, styled with the timeline's variables at `styles.css:1720-1734`) when all events share a kind, else `is-mixed` (grey, `--text-faint`) with the count drawn inside. Highlighted / dimmed / current / focused are classes; the selected, current and focused states also add a ring and a shape change so colour is never alone (spec, accessibility).
- **Clusters** (recommended by the planner, to confirm): greedy by radius in screen space. `clusterPlaces(visible, pinned)` sorts places by events descending then key, takes each unassigned place as a seed and absorbs unassigned places closer than the sum of the two radii (found through `PlaceGrid`), then places the cluster at the event-weighted centroid. `pinned` (the selected record's places, the search's current place, the keyboard-focused place) are never absorbed and never seeds' victims. Deterministic, O(n) with the grid, no flicker on a pan because the set shifts with it. A cluster is a ring with the number of **places**, distinct from a disc with a count of **events** (so "12" cannot be misread). A click zooms to fit the members (`fitView(bounds, size, pad)`); degenerate bounds (identical coordinates, no zoom separates them) open the popup of all their events grouped by place. *Alternative:* grid-cell clustering — simpler and stabler per cell, but visibly merges places that are far apart across a cell and splits near ones across an edge.
- **Labels.** `placeLabel(place, events) → "Paris · 1891–1934"` (short name by `shortPlace`, `labels.ts:67`; years by `yearText`, `labels.ts:32`, so BCE is as everywhere). `placeLabels(boxes, measure)` (pure; `measure(text)` is injected — a cached `getComputedTextLength` of an offscreen text element in the board, `text.length * 7` in tests) places labels greedily in priority order — kept places first (selected record, current, focused, hovered), then events descending, then name — to the right of the marker, else to the left, hiding a label whose box overlaps a placed label or any marker. Dimmed places' labels are hidden while a record is selected.
- **Route.** `routeOf` as D1; arrowheads at segment midpoints (a small `<path>` rotated by the segment's screen angle), order numbers drawn on the stops. Lines are straight in the projection, not great circles: at the scale of a family's moves they are indistinguishable and the code stays small. A family's route is the family record's own events only (recommended by the planner, to confirm: the alternative — adding the births of its children — is richer but makes the line a different thing for a family and a person).
- **Years range.** `src/desk/yearRange.ts` (pure): `boundsOf(events)`, `clampRange(range, bounds)`, `stepHandle(range, handle, key)` (Left/Right ±1, PageUp/PageDown ±10, Home/End), `keeps(event, range)` (span overlap; undated hidden while a range is set), `readout(range)`, `chipText(range)`. The handles are `role="slider"` elements with `aria-valuemin/max/now/valuetext` and 44 px hit areas; the chip is a `<button aria-expanded>`. The expanding chip is built beside `FloatingSearch`'s pattern (`floatingSearch.ts:22-102`: an icon that gives way to a field and returns), at the bottom left, where the zoom controls (`dom.ts:110`) are at the bottom right. A collapsed chip with a range set reads `Years: 1880–1920` (recommended by the planner, to confirm; without it the reader could not tell a range is on).
- **Selection is separate from every filter**: the range and the search only change what is drawn; `FileViews.select("map", …)` is the only path that changes what is marked.

### D10. Search, panel, keyboard

- **Search** reuses `FloatingSearch` unchanged (`change`, `step`, `info`; the placeholder is a new key `map.search`). ## Risks / Trade-offs

- [A fifth mode makes the header crowded on a phone] → buttons are Obsidian's own header actions that already wrap into the view-actions menu; the spec scenario checks five reachable buttons on a phone and the manual task looks at 320–430 px.
- [The outline looks coarse at city zoom] → decide 110 m vs simplified 50 m by screenshot in the implementation; the budget allows 50 m; tiles are the answer for street detail and are opt-in.
- [Tile servers that require a Referer/User-Agent reject the app] → documented; the plugin ships no server; failure is graceful (D7).
- [An address typed in settings is stored in `data.json` in plain text; a provider key in the URL is then in the vault's plugin data] → the description says the address is saved as typed; it is never logged, shown on the map (attribution defaults to the host only, not the URL) or sent anywhere but the tile requests.
- [A tile image request reveals the region being viewed (the family's home region)] → stated in the README and the setting's description, which is why tiles are off and have no default.
- [Writing a note on rename and creation is the plugin's first write outside the GEDCOM file] → both are explicit (a button; a rename the reader made, announced by a notice), neither overwrites, and the spec says what is written.
- [`GraphInput` reuse changes a shared input class] → the new `limits()` host method has the graph answer with today's `ZOOM`; existing graph specs and a new unit test on the class pin it.
- [Thousands of places at the world zoom] → only the view and a margin are projected; clusters are built from that set; marks are pooled; a spec counts marks (a few hundred) on a five-thousand-place file.
- [rAF glide differs from the graph's CSS glide] → both obey the same reduced-motion and reach rules from shared constants; the difference is invisible to the reader and necessary for screen-space marks.
- [SVG `aria` on hundreds of marks is noisy for screen readers] → marks are `aria-hidden` in bulk; the plot is one stop with a live region, and the places panel is the list alternative.
- [Place identity by exact text will not merge `Paris` and `Paris, France`] → by design (D2); the table is where a reader maps both spellings, one row each.

## Migration Plan

There is nothing to migrate. A workspace saved by this version with a tab in Map mode, opened by an older one, falls back as an unknown mode does (`readDeskMode` returns undefined). New settings default off/empty, so an updating reader sees no change and no request. No file is created or touched until the reader presses **Create the places table**, or renames a `.ged` that has a table. Rollback is reverting the change; a `curie.places.md` the reader created stays as an ordinary note.

4. **Following a renamed `.ged` with its table** (D3) — recommended, to confirm; the fallback is stated.
5. **Order of places** in the panel, the keyboard and the search — alphabetical (D10), to confirm.
6. **The collapsed chip reads the range** when one is set (D9).
