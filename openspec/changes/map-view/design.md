## Goals / Non-Goals

**Goals:**

- Map is a mode like the other three: same tab, same reading of the file, same selection, same memory, and no new way to select a record.
- The pure parts — coordinate reading, the places table, projection, tile planning, clustering, label collision, years range, hit testing — are plain functions with tests, in the layer `src/desk/` already uses for such things; the board is a thin DOM shell over them.
- The plugin's network promise gets no exception except one the reader switches on and can read, and the first request is the reader's.
- Desktop and phone from the first commit.

**Non-Goals:**

- A reusable map engine. The board draws what this view needs; nothing else is promised.
- Any change to the language service, the validator or the codemirror package.
- Persisting the years range or the search text (kept in the tab's board, not saved, as the list keeps its filter).

## Decisions

### D1. The model: `FileMap`, built from the index and the places table

A new pure module `src/desk/fileMap.ts` builds, once per `(GenealogyIndex, PlacesTable)` pair (a `WeakMap` per index, then per table object, as `fileTimelineOf` does at `fileTimeline.ts:502-512`), a `FileMap`:

- `places`: one `MapPlace { key, name, coordinates?, events }` per distinct place. `key = placeKey(text)` (trim, collapse white space, NFC, `toLowerCase`); `name` is the first spelling met in file order. Coordinates: the first valid `MAP` among the place's events in file order, else the table's, else none (priority per the user's decision 1).
- `events`: `MapEvent { record, kind, tag, label, year?, span? , order }` for every event with a place: the events of `person.events` (`Person.events`, `types.ts:181`) and of `family.events` (`types.ts:151`), each once (a marriage is the family's, not one per spouse). `kind` is `kindOf(tag)`, which `fileTimeline.ts:117` exports for this (it is private now; exporting is the only change to that file). `year` is the earlier of `date.year` and `date.end`, `span` is `[min, max]` of the two where `end` exists, so that a period and a `BET … AND …` overlap a range alike. The model does **not** use `FileTimeline.marks`, because marks exist only for dated events (`markOf`, `fileTimeline.ts:134`) and an undated event must still count and sit at its place.
- **Memoisation.** `fileMapOf(index, table)` builds the model once per index and table object (a `WeakMap` pair). `fileTimelineOf(index)` is touched only when a branch is asked for, never for the whole file, so the first open on a 20 000-person file does not run the timeline's scan.
- `scope(branch)`: the set of events whose record is a person in `fileTimelineOf(index).branch(focus, up, down)` (`fileTimeline.ts:64`), or a family with a spouse in it; the whole file when there is no focus. `LARGE_FILE`/`initialFocus` (`fileTimeline.ts:74,493`) are **not** applied: a map aggregates, so it opens on the whole file whatever its size.
- `route(record)`: the dated events of a person (own plus the families they are a spouse in, `Person.unions[].events`, `types.ts:169`) or of a family, with coordinates, in the range, ordered by `(year, order)` where `order` is the position of the event's line in the whole file (so a person's birth and a family's marriage of one year tie-break by the file, not by record), consecutive same-place events merged into one **stop**, each stop carrying its order numbers (the numbers count stops, not events).
- `mapSelection(index, xref)`: the xref where it is a person or family, else null (the pure twin of `listSelection`).

`PersonEvent` gains `coordinates?: { latitude, longitude }` read in `eventsOf` by a new `readCoordinates(place)` beside it in `src/genealogy/` (`childOf(place, "MAP")` → `LATI`/`LONG` → `readDegrees(text, axis)`, a half pair or an invalid value giving `undefined`). **One rule for the file and the table**, in `src/genealogy/coordinates.ts` as `readDegrees(text, "lat" | "lon")`: trim; a decimal with a point or a comma; either an optional sign alone, or one letter (either case) before or after the number with optional white space and no sign; the letter must belong to the axis (`N`/`S`, `E`/`W`); `S` and `W` negate; `S0` is `0`, never `-0`; the range is checked. So `N 10.5`, `n10.5`, `10,5 e` and `-70.67` read; `W-1.5`, `N 91` and `10.5 E` as a latitude do not. The placesTable parser uses the same function. (The file's own `LATI 52.2` with no letter is invalid GEDCOM and the validator says so; reading it is harmless and keeps one rule.) `eventsOf` today calls `childOf(child, "PLAC")` twice (`events.ts:23-25`); it binds it once. Only the model reads syntax-tree symbols, so the board never touches `DocumentSymbol`.

*Alternative considered:* read `MAP` in `fileMap.ts` from the symbols. Rejected: the model is the one place that reads `PLAC` (`genealogy-read-model` says events are reported from a named set of structures), and `api.ts` or a later card could want the coordinates.

### D2. Place identity

Two spellings are one place when `placeKey` agrees: case-folded and white-space-collapsed, not accent-folded and not comma-normalised (`Paris,France` and `Paris, France` differ; the table is where a reader fixes that). Recommended by the planner, to confirm: this is the smallest rule that cannot merge two places the file keeps apart; a looser one (accent-folding) would merge `Orléans` and `Orleans`, which may be two towns in a historical file. The search folds accents (D10) because finding needs it; identity must not.

### D3. The places table: format, location, lifecycle

`<name>.places.md` in the `.ged`'s folder (`curie.ged` → `curie.places.md`; `.gedcom` the same; the extension matched case-insensitively, `.GED` included; `a.ged` and `a.gedcom` in one folder **share one table** — stated, not special-cased). A plain note, so the reader edits it in Obsidian's own editor, with the table editor in Live Preview. Format:

```
| Place | Latitude | Longitude |
| --- | --- | --- |
| Warsaw, Congress Poland | 52.2297 | 21.0122 |
| Paris, France | 48.8566 | 2.3522 |
| Santiago, Chile | S33.4489 | W70.6693 |
| Stockholm, Sweden |  |  |
```

Rules are in the spec (`genealogy-map`, *The places table is a note next to the file*): first table of the note; header and delimiter skipped by position (so `Место | Широта | Долгота` works); `\|` escapes a bar; decimal point or comma; optional hemisphere letter before or after, never with a sign; out-of-range or empty gives no coordinates; first row of a repeated place wins; anything else in the note is ignored. Pure parser `parsePlacesTable(text): PlacesTable` never throws and returns `{ rows: Map<key, Coordinates | null>, names }`; `placesTablePath(gedPath)`; `placesTableText(places, collator, note)` builds the created note.

*Why a note and not JSON or a sidecar:* the reader asked for hand-editable; a Markdown table is editable in Obsidian with no tooling, is searchable, syncs and is diffable. *Why positional header:* the file is created in English but a reader of another language will rewrite the header.

**A reader-owned note outside the file (accepted).** `PRODUCT.md` Principle 1 and `CLAUDE.md` say the file is the source of truth and no second genealogy database is built. The places table is neither a conversion of records nor a database: it is a note the reader creates by an explicit action, holds coordinates the file does not carry, never shadows the file (a `MAP` in the file wins) and is read, never cached or written without a button. The planner's decision, to be confirmed: accepted, and `PRODUCT.md` is updated to say so (task 9.x).

**Lifecycle (hosted by `main.ts` and the tab, not by the pure code).** The table has **three states in the tab: not read yet, read (with rows or none), absent**. The empty state is shown only after a read has completed (`undefined` is not `absent`). The tab asks the host for the table text when it enters Map mode and whenever the host reports that a path changed (`vault.on("modify" | "create" | "delete" | "rename")` registered once in `main.ts`, the `create` listener only after `workspace.onLayoutReady` so the initial vault scan does not fire it for every file; the read after a `modify` is `vault.read`, not `cachedRead`, so it never returns stale text). A **folder rename** fires one event for the folder (`main.ts:252-259` already unfolds it with `descendantPaths`), so every tab re-reads its table path after any rename and, for a folder, after the unfolded paths: the tab compares its table path before and after rather than waiting for an event naming the note. All of `vault.getAbstractFileByPath`, `cachedRead`, `create`, `on(...)`, `fileManager.renameFile` and `workspace.getLeaf(...).openFile` exist well below 1.8.7, so no floor is touched. Reading is cheap and debounced to one read per change.

**Rename (decided by the planner, to confirm).** When a `.ged` is renamed or moved (the existing rename event) and `<old>.places.md` exists and `<new>.places.md` does not, the plugin renames the table with `fileManager.renameFile` (which updates links to it) and gives a notice. Otherwise both stay. *Why:* a table is useless once separated from its file, and a silent orphan makes a map "lose" its coordinates with no visible cause. *Cost:* the plugin renames a note the reader owns — one the reader created by an explicit action, named after the file, and the notice says so. *If not confirmed:* the table is found by name only, a renamed `.ged` loses it, and the empty-state message names the path the table is expected at.

**Create (decision 8).** `Create the places table`: the host calls `vault.create(path, text)`; on "already exists" (a race or a stale view) it opens the existing note and creates nothing. The text is a one-line note in the language of the plugin (`map.table.note`) above the table; headers always English. Rows: the distinct places the file has **no `MAP` for** (recommended by the planner, to confirm — decision 8 says "the file's distinct place names"; rows for places that already have a `MAP` would never be read, since the file wins, and would only make the table longer to edit), named as first written, sorted with the plugin language's collator. When the note exists and no place has coordinates, the button reads *Open the places table*. The creation writes that one note and nothing else.

**Append (decided by the planner).** The Places of the list (D10) offers **Add the N places that have no row** where the table exists and some places that the file maps nowhere have no row: the pure `appendMissingRows(text, missing)` appends rows to the first table (after its last row), or the header, delimiter and rows at the end of a note with no table, and changes nothing else; the host writes through `vault.process` (atomic read-modify-write). Hand-editing remains possible and primary; the action only saves typing and typos.

### D4. The outline: Natural Earth, packed

**Source (pinned; the planner decides 110 m first, by a screenshot of the harness):** Natural Earth `ne_110m_land`, version 5.1.1 as published at `https://naciscdn.org/naturalearth/110m/physical/ne_110m_land.zip` (public domain), whose SHA-256 the script records and checks; the script fails on a different checksum. (The pinned version and checksum are fixed in `scripts/outline.mjs` when the source is first fetched, and the design's *Implementation* section records them.), land polygons only: no borders, which would mislead for historical files and are out of scope by decision 9, no lakes, no labels.

**Packing.** A generator script `scripts/outline.mjs` (outside `src/`, so Node is allowed, as for `harness/build.mjs`) takes the GeoJSON path as an argument, drops rings under a small area, simplifies to a 0.1° tolerance, quantises longitude and latitude to 0.05° into integers, delta-encodes each ring, writes the deltas as zigzag varints, and base64-encodes the bytes into a generated module `src/desk/mapOutlineData.ts` (one exported string, committed). The reviewer measured 11–14 KB of base64 for 110 m; the 40 KB figure in the proposal is a ceiling, the budget is 300 KB (decision 3) and the spec requires ≤ 300 KB. **Antarctica:** the Mercator clamp is ±85.05113°, so land below it is cut at the clamp in `outlinePath` (rings are clipped to latitude ≥ −85.05113 before projection, closing along the bottom edge), never drawn off the world. **Lint:** `scripts/**` is added to the `ignores` of `eslint.config.mjs` (Node built-ins, `process` and `console` are legitimate in a build script, as for `harness/build.mjs`, which is already ignored through `harness/**`); `scripts/` is outside `tsconfig` and outside `src/`. `decodeOutline(data): Ring[]` (pure; `atob` exists on mobile) yields rings in degrees; `outlinePath(rings)` projects them to one SVG path in world units `[0, 256]²` (Web Mercator, latitude clamped to ±85.05113°), built once and reused for every draw. The source file is not committed; the script and its command line are documented in the README *Development* section, with the licence note in the README under *License* (the README has no Credits section): "Land outline from Natural Earth (public domain)". The generated module carries no comment; the licence is in the README, where a reader looks for it.

*If 110 m is too coarse once seen at city zoom:* the same script runs on `ne_50m_land` at 0.02° tolerance; the budget allows it (50 m land, simplified, is ~100–200 KB). The task makes the choice by a screenshot, and a unit test pins the generated size under the budget either way. *Alternative rejected:* an SVG world map asset (large, hand-drawn, unclear licence) and any runtime download (violates decision 2).

### D5. Projection, view and zoom

Web Mercator in a pure `src/desk/mapProjection.ts`: `project(lat, lon) → [wx, wy]` in `[0,1]²`, `unproject`, clamping latitude to ±85.05113°. The **view** is `{ x, y, k }` in the same shape the graph uses (a CSS-like translate and scale), where the world is `256·k` pixels wide, `k = 2^zoom`. This is deliberate: `GraphInput` (drag, pinch, wheel; `graphInput.ts:27-170`) is written against `{x, y, k}` and a host that applies it, so the map reuses it by making the zoom limits the host's: `GraphInputHost` gains `limits(): { min: number; max: number }` in place of the import of `ZOOM` (`graphInput.ts:2,145`). The graph answers with its `ZOOM`, so its behaviour does not change; a test pins that.

What is **saved** (in `DeskState.map`, `MapState = BranchScope & { view?: { lat, lon, zoom } }`) is the centre and zoom, not the pixel transform: a tab restored in a different width shows the same place, which `{x,y,k}` would not. It is rounded (lat/lon to 4 decimals, zoom to 2) and read defensively as `readGraphState` does (`fileGraphView.ts:47`).

**First view and Fit.** A map with no saved view opens **fitted** to the places of the scope and range (`fitView` over their bounds with a margin, never closer than zoom 6 for a single place, the world for none). The **Fit** button and the `0` key do the same. A change of the branch scope refits; a change of the years range, the search or the table does not move the map. A saved view wins over the fit until Fit or a scope change. The board keeps a `fitted` flag (not saved): the view is saved on the first user move and never before.

Limits: the minimum zoom is the one at which the world just fits the tab (never smaller); the maximum is 12 without tiles and 18 with them (the outline at street scale is meaningless; a view saved above the limit is clamped on read). The centre is clamped so some of the world is always in the tab. No world wrap (non-goal): points at ±180° sit at the two ends of the one world. *Alternative:* wrap with duplicated marks — doubles drawing and selection ambiguities for little gain in a genealogy tool.

### D6. Drawing: an SVG shell, screen-space marks, virtualised

One `<svg>` per board with three layers: the **base** (the outline as one `<path>` inside a `<g>` carrying the world transform, `vector-effect: non-scaling-stroke`), the **tiles** (an HTML layer under the SVG, see D7), and the **marks** (points, clusters, lines, arrows, labels) in screen space, positioned by projecting each place through the current view. Marks stay a constant size at any zoom, which a transformed group cannot give without per-mark counter-scaling.

Only what is in view and in a margin is projected and drawn. Clusters are made from that set (D9), so the document holds a bounded number of marks (a few hundred) whether the file has fifty places or five thousand; `PlaceGrid` (`src/desk/mapHits.ts`, pure) is a spatial hash over world coordinates built once per model, answering "the places in this rectangle" without scanning all, and also the pointer hit test. Marks are pooled by key and their `transform` updated during a drag, rather than rebuilt; the label pass runs when the view settles (a frame after the last change) and not on every pointer move.

*Why not canvas:* the timeline is SVG with a virtualised window, the Playwright specs query elements, and accessibility names and focus rings are free on elements. At a few hundred marks SVG is fast enough; canvas would be the next step if a measurement says otherwise (task 7.x measures, as the timeline's specs do).

**Glide.** Not the CSS transition of the graph (`graphCanvas.ts:619-680`), because that scales one element and the marks are screen-space. A small `glide` interpolates the view in log-zoom and screen centre with an ease-out over `GLIDE_MS` using `requestAnimationFrame`, re-projecting the pooled marks each frame; it jumps where `prefersReducedMotion(doc)` (`dom.ts:132`) or where the move is longer than `GLIDE_REACH` screens (the same rule as the graph, `graphCanvas.ts:639-645`); a drag, the wheel or a key takes over from the point reached. `GLIDE_MS` and `GLIDE_REACH` are exported from `graphCanvas.ts` (they are module constants today) so both boards share them. The interpolation is a pure function in `mapProjection.ts`.

### D7. Tiles: an image layer, off by default, never in the way

Settings: `mapTiles: boolean` (off), `tileUrl: string` (empty), `tileAttribution: string` (empty) — new keys in `GedcomSettings` (`settingsData.ts:9-18`), `DEFAULT_SETTINGS`, `parseSettings` and `changedSetting`. A text value is stored **as typed** (capped at 2048 characters) and judged at use, but the **settings row applies it only on blur or Enter, or after 700 ms without typing** (`updateSettings` saves on every change and refreshes the editor, `main.ts:548-560`, `GedcomView.ts:339-366`; a partial URL can become valid and be requested, so the row commits late). The validator in `applySettings` (the method that carries a setting into the open tabs; not `settingsChanged`) takes the address only when it is **`https://` with all of `{z}`, `{x}` and `{y}`**, and nothing is requested before. `changedSetting` accepts a value only when `parseSettings` returns it unchanged (`settingsData.ts:52-62`), so trimming or validating on save would reject every half-typed address. `tileTemplate(settings): string | null` (pure, in `src/desk/mapProjection.ts` or `mapTiles.ts`) returns the trimmed address when it begins with `https://` (case-insensitive), holds `{z}`, `{x}` and `{y}`, and `new URL(...)` accepts it with `0/0/0` put in; else null. A non-empty address that fails shows *The tile server address is not valid* in the settings row's description area and on the map's status; nothing is requested.

`planTiles(view, size, ring, maxZoom)` (pure) returns the `{z, x, y}` keys covering the view plus a ring, at `z = clamp(round(zoom))`, with their world rectangles; `x` wraps are not needed (no wrap), `y` out of range is dropped. The tile layer is a `<div>` under the SVG with the same translate/scale as the base; each tile an `<img>` (`crossorigin` unset, `referrerpolicy="no-referrer"`, `decoding="async"`, `alt=""`) sized in world units. `<img>` rather than SVG `<image>` because error and load events are dependable on every engine the app runs. Requests start only when the view has settled (150 ms without change) so a drag or a glide does not queue a fetch per frame; tiles that leave the planned set have their `src` cleared. Tiles are drawn half a pixel larger than their cell so no hairline seam shows between them. The count is `(ceil(w/256·k') + 2)·(ceil(h/256·k') + 2)` for a one-tile ring at integer zoom: about 63 tiles for a 1400×900 view, up to about 99 at a half level (rounded zoom), about 30 on a phone; the test bound is under 120.

The outline stays above the tiles as a line without fill (`.is-tiles` on the root). `TileFailures` (pure, clock injected): a failed key is not retried for 60 s while it stays planned; three failures within ten seconds with no success set the status *Tiles could not be loaded*; a success clears it. A tile error never throws and never blocks anything: marks are drawn from the model before any tile is asked for, and the tile layer shares no promise with them.

**Privacy statement** (README *Privacy*, `README.md:227-239`, and the settings description): "With **Load map tiles from the web** on, the map asks the tile server you name for the images of the part of the world in view. That server learns the tile numbers — which say what part of the world you are looking at — and your IP address, as any website does. No place name, person or date is sent, and nothing is sent while the setting is off or the address is empty." The text *It makes no network request until you ask it to* stays true; the "one thing you can ask for" becomes two. `http://` is refused as it is for images.

**Attribution** (recommended by the planner, to confirm): the map must show attribution when tiles are on, and the plugin cannot know what a reader's server requires, so the reader supplies it in **Tile attribution**; empty, the map shows the server's host name, so attribution is never absent. It is plain text set with `setText`, never taken from the server and never HTML. Known limit: some public servers (for example `tile.openstreetmap.org`) require an identifying `Referer` and `User-Agent` that a desktop app cannot always supply; a reader who hits that uses a provider that allows it. The README says which setting to look at and ships no server.

### D8. Settings rows

### D9. Points, clusters, labels, route (pure modules)

- **Size and colour.** `radius(n) = min(22, 5 + 1.7·√(n − 1))` px; the hit target is 44 px (decision 7). Colour: the kind's class (`is-birth`, `is-death`, `is-marriage`, `is-other`, styled with the timeline's variables at `styles.css:1720-1734`) when all events share a kind, else `is-mixed` (grey, `--text-faint`) with the count drawn inside. Highlighted / dimmed / current / focused are classes; the selected, current and focused states also add a ring and a shape change so colour is never alone (spec, accessibility).
- **Clusters** (decided by the planner): greedy by radius in screen space; **on a coarse pointer the spacing is `max(sum of radii, 22)` px** so two targets never overlap, and a press resolves to the **nearest** point or cluster within its 44 px target through `PlaceGrid.nearest`, not to whichever SVG element is on top. The count of marks is bounded by a function of the viewport: at most `ceil(w/s)·ceil(h/s)` cells with `s` = 22 on a coarse pointer and 10 otherwise (plus the pinned ones), plus a margin ring; the 5000-place spec asserts under 600 at the world zoom as the practical figure. `clusterPlaces(visible, pinned)` sorts places by events descending then key, takes each unassigned place as a seed and absorbs unassigned places closer than the sum of the two radii (found through `PlaceGrid`), then places the cluster at the event-weighted centroid. `pinned` (the selected record's places, the search's current place, the keyboard-focused place) are never absorbed and never seeds' victims. Deterministic, O(n) with the grid, no flicker on a pan because the set shifts with it. A cluster is a ring with the number of **places**, distinct from a disc with a count of **events** (so "12" cannot be misread). A click zooms to fit the members (`fitView(bounds, size, pad)`); degenerate bounds (identical coordinates, no zoom separates them) open the popup of all their events grouped by place. *Alternative:* grid-cell clustering — simpler and stabler per cell, but visibly merges places that are far apart across a cell and splits near ones across an edge.
- **Labels.** `placeLabel(place, events) → "Paris · 1891–1934"` (a period such as `FROM 1891 TO 1894` counts both ends: `Paris · 1891–1894`) (short name by `shortPlace`, `labels.ts:67`; years by `yearText`, `labels.ts:32`, so BCE is as everywhere). `placeLabels(boxes, measure)` (pure; `measure(text)` is injected — a cached `getComputedTextLength` of an offscreen text element in the board, `text.length * 7` in tests) places labels greedily in priority order — kept places first (selected record, current, focused, hovered), then events descending, then name — to the right of the marker, else to the left, hiding a label whose box overlaps a placed label or any marker. Dimmed places' labels are hidden while a record is selected.
- **Route.** `routeOf` as D1; arrowheads at segment midpoints (a small `<path>` rotated by the segment's screen angle), order numbers drawn on the stops. Lines are straight in the projection, not great circles: at the scale of a family's moves they are indistinguishable and the code stays small. A family's route is the family record's own events only (recommended by the planner, to confirm: the alternative — adding the births of its children — is richer but makes the line a different thing for a family and a person).
- **Years range.** `src/desk/yearRange.ts` (pure): `boundsOf(events)`, `clampRange(range, bounds)`, `stepHandle(range, handle, key)` (Left/Right ±1, PageUp/PageDown ±10, Home/End), `keeps(event, range)` (span overlap; undated hidden while a range is set), `readout(range)`, `chipText(range)`. The handles are `role="slider"` elements with `aria-valuemin/max/now/valuetext` and 44 px hit areas; the chip is a `<button aria-expanded>`. The expanding chip is built beside `FloatingSearch`'s pattern (`floatingSearch.ts:22-102`: an icon that gives way to a field and returns), at the bottom left, where the zoom controls (`dom.ts:110`) are at the bottom right. A collapsed chip with a range set reads `Years: 1880–1920` (decided by the planner; without it the reader could not tell a range is on). A saved range is clamped to the new bounds (`clampRange`) whenever an edit moves them, and the range is held by the tab's board, not saved. The range changes recompute counts and marks once per animation frame (`requestAnimationFrame`-throttled), not per drag step.
- **Branch of (B1).** Map's scope row has, besides `BranchScopeBar` (shown once a focus is set), a button **Branch of {name}** that sets the branch focus to the selected person (disabled with none or a family) and a **Whole file** control that clears it; `MapState = BranchScope & { view? }` keeps `focus`, `up`, `down` as the other views do, and the scope refits (D5).
- **Selection is separate from every filter**: the range and the search only change what is drawn; `FileViews.select("map", …)` is the only path that changes what is marked.

## Risks / Trade-offs

- [A fifth mode makes the header crowded on a phone] → buttons are Obsidian's own header actions that already wrap into the view-actions menu; the spec scenario checks five reachable buttons on a phone and the manual task looks at 320–430 px.
- [The outline looks coarse at city zoom] → decide 110 m vs simplified 50 m by screenshot in the implementation; the budget allows 50 m; tiles are the answer for street detail and are opt-in.
- [Tile servers that require a Referer/User-Agent reject the app] → documented; the plugin ships no server; failure is graceful (D7).
- [An address typed in settings is stored in `data.json` in plain text; a provider key in the URL is then in the vault's plugin data] → the description says the address is saved as typed; it is never logged, shown on the map (attribution defaults to the host only, not the URL) or sent anywhere but the tile requests.
- [A tile image request reveals the region being viewed (the family's home region)] → stated in the README and the setting's description, which is why tiles are off and have no default.
- [Writing a note on rename and creation is the plugin's first write outside the GEDCOM file] → both are explicit (a button; a rename the reader made, announced by a notice), neither overwrites, and the spec says what is written.
- [`GraphInput` reuse changes a shared input class] → the new `limits()` host method has the graph answer with today's `ZOOM`; existing graph specs and a new unit test on the class pin it.
- [Thousands of places at the world zoom] → only the view and a margin are projected; clusters are built from that set; marks are pooled; a spec counts marks (a few hundred) on a five-thousand-place file.
- [rAF glide differs from the graph's CSS glide] → both obey the same reduced-motion and reach rules from shared constants; the difference is invisible to the reader and necessary for screen-space marks.
- [SVG `aria` on hundreds of marks is noisy for screen readers] → marks are `aria-hidden` in bulk; the plot is one stop with a live region, and the Places of the list is the list alternative.
- [Place identity by exact text will not merge `Paris` and `Paris, France`] → by design (D2); the table is where a reader maps both spellings, one row each.

## Migration Plan

There is nothing to migrate. A workspace saved by this version with a tab in Map mode, opened by an older one, falls back as an unknown mode does (`readDeskMode` returns undefined). New settings default off/empty, so an updating reader sees no change and no request. No file is created or touched until the reader presses **Create the places table**, or renames a `.ged` that has a table. Rollback is reverting the change; a `curie.places.md` the reader created stays as an ordinary note.

## Decisions taken on the places list (2026-11-05)

The user asked whether the list of places could live in the *List* view. Taken as given:

1. **A click on a Places row only marks the row.** It does not switch to the map, move it or select a record; the record card stays as it is.
2. **The panel is removed from the map entirely.** Everything about the list of places lives in the List.

Refined by the planner, each reversible:

- **The kind is the fourth button, after Sources**, with the columns *Place, Events, Years, Coordinates*; it lists every place of the file, mapped or not, alphabetically with the language's collator until a column is chosen. The third press of a header returns to that alphabetical order, so the compact sort menu names its empty choice *Alphabetical* on this kind in place of *File order*.
- **The mark for a place with no coordinates is the list's mark for *no sources*** (a ring with a text alternative *No coordinates*; written out beside it on two-line rows). While the places table is unread the list shows only the coordinates the file gives and no mark, and hides the table's actions, so nothing flashes a wrong state.
- **The table's actions sit at the end of the row of the kind buttons**, shown only on this kind, so there is no new toolbar row; on a narrow tab they wrap under the buttons and are 44 px tall on touch.
- **The selected place is list-local state**, a place key saved with the list's kind and sorts (`ListState.place`), dropped when the kind changes or the file no longer holds it. A record selected elsewhere leaves the list on Places, since no record has a row there; the row of that record is marked when People, Families or Sources is shown next.
- **The counter is a button that clears the list's search** and shows the Places, so the places are visible; the sort of each kind is kept. It still counts the places of the map's scope; the list shows all places of the file.
- **The search folds as the map's** (`foldText`): case, marks, the transliteration table.
- **Sort by Coordinates** orders by whether the place has any (none first when ascending), so a reader finds the places that need coordinates.

## Implementation

Deviations from the plan as written, found while building it.

- **The outline source is Natural Earth 4.1.0**, not 5.1.1: `ne_110m_land.zip` at `https://naciscdn.org/naturalearth/110m/physical/ne_110m_land.zip`, SHA-256 `1926c621afd6ac67c3f36639bb1236134a48d82226dc675d3e3df53d02d2a3de`; the script takes the unzipped `.shp` (it reads the shapefile itself, so there is no GeoJSON step) and checks its own SHA-256, `8689e6932b8e370e2ca4587cf3ba21e460b1235db37b6ed3c172c35b4a6088de`. 110 m was kept after looking at the harness at world and country zoom: 115 rings, 13 972 characters of base64; the coast is coarse at city zoom, where tiles are the answer.
