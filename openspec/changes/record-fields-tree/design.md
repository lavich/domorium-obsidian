## Context

See `proposal.md` for why and for what the user decided. What the code does today, as far as this change touches it:

- A person's card is `renderPersonPage` (`src/desk/personPage.ts`): a heading, then names, the facts as event rows and detail rows, the family, notes, related people, media, a folded timeline, folded identifiers and other data, then evidence (`src/desk/evidence.ts`, drawn by `recordCard.ts`). A family card (`familyPage.ts`) and a source card (`sourcePage.ts`) are built the same way from their own sections. `renderSourcePage` takes no `open`, `folded` or `selected`, and `drawRecord` passes it none.
- `index.record(xref)` already returns the whole record as `RecordLine`s — tag, text, pointer, nested children, `range` (`src/genealogy/recordLines.ts`, `types.ts`). The `range` of a line is its whole subtree, `CONT` and `CONC` included (probed against `@domorium/language-service` 2.3.1). Sections that retell lines read the record through `claims.ts` (`unclaimed`, `PERSON_CLAIMED`) to find what no section drew.
- `src/desk/detail/lineView.ts` draws any line as a label and a value, a pointer as a link (`renderPointer`, which also draws a shared note's text and children inline), a note folded (`renderNoteText`, keyed by the order notes are drawn in), a value as a read-only field (`renderField`, `fields.ts`). It nests with a `gedcom-detail` grid; it has no node, no summary, no control. `names.ts` is where a name's type is turned into words (`nameTypeLabel`) and where the placeholder for no name is used.
- The card is torn down and redrawn on every change; its scroll, its folds (`data-open` on the root, `foldsOf` in `recordCard.ts`) and the focus (`data-focus-key`) are carried across; folds and scroll reset when another record is shown, including on Back (`recordCard.ts`, `shown !== previous`).
- A fact is an event or an attribute a card can open (`factsOf` in `personPage.ts`, `familyFacts`): `fact.event.range` is the range of its line and `fact.eventId` is what opens its card, through `host.openRecord(eventId)` (`factRow.ts`); a fact with no `eventId` is inert. `host.select` and `GedcomView.selectedFact` are not used by any row today, and `options.selected` only chooses what the heading's *Show in source* selects.
- A place in an event row is a link to the place card (`personPage.test.ts`, `tests/desk.spec.ts`).
- The event card (`eventPage.ts`) uses `renderNotes`, `renderRelated` and `renderOther`; `NOTE_TAGS` and `RELATED_TAGS` come from `claims.ts` for `notes.ts`, `related.ts` and `eventDetails.ts`. The family section and the place card draw the event row of `factRow.ts`.
- `RecordCardView` is created for each leaf (`DeskViews.ts`); `CardView` holds `setIcon` and `openNote` only.
- Reading needs no new data; editing calls the language-service methods of lavich/domorium#522 (`describeStructure`, `addStructure`, `setValue`, `removeStructure`, `validateValue`).

## Goals / Non-Goals

**Goals:**

- One renderer that draws a record's lines as they are, so that rows can be edited without a new layout.
- A card that fits 320 pixels and a phone and that does not show a control until the reader is there.

**Non-Goals:**

- A generic tree widget for other views; the renderer is the card's and is written for `RecordLine`.
- Removing `selectFact` and `selectedFact`, which nothing uses; left as they are.

## Decisions

**A new renderer, `src/desk/detail/tree.ts`, built from the pieces `lineView.ts` already has.** It reuses `renderPointer`, `renderField`, `valueText` (exported for this; it gains the line's parent so that the type of a name is read as one only under a `NAME`, with the no-name placeholder moved in from `names.ts`) and `tagLabel`, and adds what a tree needs: a node with a control, a summary, a depth, lazy children. Alternative: extend `renderLine`. Rejected: its grid cannot carry a node's header, and the event card still needs it as it is.

**The tree draws every line and claims nothing.** The family section, the media and the timeline stay, so a line that a section also tells — `FAMS`, `FAMC`, `HUSB`, `WIFE`, `CHIL`, `OBJE`, `REPO`, an event's citation — shows in both. Alternative: leave out of the tree the lines a section draws, as `claims.ts` does today. Rejected: it breaks "the file's order, nothing left out" and leaves holes in the order. `PERSON_CLAIMED`, `unclaimed` and `INFO_TAGS` go; `NOTE_TAGS` and `RELATED_TAGS`, which the event card's `notes.ts`, `related.ts` and `eventDetails.ts` still read, move into those modules and `claims.ts` is deleted.

**A node's key is its place in the record, not its line number.** `NAME[1].TYPE[0]`: the tag and the index among siblings of that tag, from the record's opening line, which is the root and has the empty key, so that the keys of its children are the ones written here. It does not move when a line above changes the file's numbering, which a number does; it does move if a sibling of the same tag is inserted above it, and then the reader's choice falls on the neighbour — accepted. A note's folded state is keyed `note:<node key>`, replacing the draw-order counter `renderNoteText` uses, which lazy drawing would make depend on the order the reader opened nodes in; it is kept in the session with the nodes.

**The reader's choices are kept per record in a session object the plugin owns.** It holds, for the last twenty records shown (by file path and record, which `renderRecordCard` already has as `shown`), which nodes and notes differ from the default. It lives on the plugin (`main.ts`, reached through `DeskViewsHost.session()` and the `CardView` literal built in `DeskViews.ts`) because the card view is made for each leaf and a leaf's end would drop it; it is lost when the plugin reloads. Alternative: `data-open` on the root as the folds do. Rejected for the tree: it is cleared when another record is shown, and the reader opening `Birth`, looking at Pierre and selecting Marie again would find her tree shut. The folds of the timeline keep the old behaviour. Alternative: a setting. Rejected: a persisted key and a settings row for something changed in passing.

**Closed nodes draw their children when first opened, and every node is closed at first.** A person with a hundred lines would otherwise draw several hundred rows at once on a phone; `lazyFold.ts` is the precedent. The container a node controls stays in the document, empty, so that its `aria-controls` points at something. *Open every node* is built from the `RecordLine`s, not from the document, and draws what is beneath each node as it opens; the Playwright spec times it as well as the first draw. A test opens a node before it looks beneath it. Alternative: open the first level. Rejected after the plan review: a node shows its summary only while closed, so the dense row — date and place of an event — would never show by default, and a person would draw three or more rows per event.

**The summary of a node is the plugin's, built from the lines it already has.** For a line the page knows as a fact — by the same line-number lookup that gives the label its card — the value other than `Y`, the date as the file writes it and the place as the file writes it, joined by a dot, leaving out what the line does not state; for any other node the value, a name without its slashes, a pointer node the record's name; for a value of several lines its first. It is shown only while the node is closed; an open node shows its value and the substructures the rest. A closed node whose line cites a source carries the quiet dot the event row has, with the same accessible name, so that the reader still sees at a glance which facts rest on a source. The place is not shortened to the heading's short form: the summary is one line that the panel cuts with an ellipsis, and the place stays a link while it is shown. Alternative: decide "is a fact" by tag. Rejected: `TITL` is in `PERSON_EVENT_TAGS` and a source's `1 TITL` would be taken for an event.

**A fact's label is a button that opens its card, and a place is a link.** The tree is given, once per page, a lookup from a line's number to the fact the page knows on it, with its `eventId`, from `factsOf` or `familyFacts`. The button calls `host.openRecord(eventId)`, which is what the event rows do, and a fact with no `eventId` is plain text, as `factRow.ts` does. The value of a `PLAC` line, and the place in a closed summary, link to the place card by the same id `placeAt` gives; a place the card does not know is text. The tree marks no row as selected: no fact is selected while a person's tree is drawn, because selecting one shows its card.

**No tag is shown, and a label fallback is not a tag.** The tree shows no tag the standard names. A tag the standard does not name, or a custom one, is the label itself, as `tagLabel` does today. There is no control to show tags.

**Node arrows and the toggle always in view.** A node's arrow is a real button, always shown in the app's collapse-icon colour, named by its row with `aria-expanded` and `aria-controls`, with a focus ring and a 44-pixel target on touch; a press on a node's header outside its controls toggles the node as the app's explorer does. The one control that acts on the whole tree, the icon toggle, is always shown in a header above the first row: `div.gedcom-tree-bar.nav-header` holding `div.nav-buttons-container` holding the toggle, a `div` with the `clickable-icon nav-action-button` classes, `role="button"` and `tabindex="0"`, which Enter and Space press. The header and the button take the app's own rules, so the plugin's stylesheet has none for the bar, no hover reveal and no touch sizes of its own; the harness palette carries a small shim of those rules. Alternative: a hover-revealed button, as the first version had it. Rejected: the reader asked for it never to be hidden. There is no control that acts on a single row: the heading keeps the card's *Show in source*, and a pointer to a record not in the file keeps the action on the pointer itself. The row reserves the arrow's column at its start, whether it is a node or a line, so that labels of one depth start at one place. Rows are set apart by `var(--size-2-2)`, the guide of the children running through the space; a row under the pointer takes `--nav-item-background-hover` and never `--nav-item-background-selected`, and a press leaves no highlight, so no row-last-pressed state is kept. Alternative: a "…" menu per row, or a *Show in source* on each row. Rejected: one more control on every row.

**A disclosure, not an ARIA tree.** A node's control is a button with `aria-expanded` and `aria-controls`, kept apart from the label, which may itself be a button (a fact) or contain a link (a place), because a button cannot hold another control; for a fact the chevron is therefore the only way to open the node, and pressing the label opens the event card. Rows are plain blocks in the tab order. An ARIA `tree` role promises roving focus and arrow keys, a second keyboard model on a card read with Tab. Alternative: `role="tree"`. Rejected for this step; revisited with editing.

**Focus is kept across a redraw by keys on every control the tree draws.** Each node's chevron, each fact's label, each place link and each pointer link carry a `data-focus-key` — `t:<node key>`, `t:<node key>:label`, `t:<node key>:place`, `t:<node key>:link` — so that the card's existing restoring puts the focus back on the control the reader used. A pointer link in the tree never reuses the record's identifier as its key, because the family section's relatives do and the card's restoring takes the first match.

**A shared note's pointer is drawn as today.** `renderPointer` draws the note's text and the lines beneath it inline; they belong to another record, are not nodes. A pointer to a record not in the file shows the action `renderPointer` already adds; a closed node shows the same action in its summary, and an open node only on the pointer, so there is one at a time.

**Indentation stops after the fourth level beneath the root.** A node's depth sets `data-depth`, the root being 0, and the CSS stops the step after the fourth nested group of children, so a line six levels deep keeps the width of one at four. A guide of one pixel in the border colour joins a node to its children; no colour band, no card around a node. A value written right to left is laid out with `dir="auto"`.

**Removed code goes in the same change.** `names.ts`, `recordInfo.ts` and `claims.ts` are deleted (their uses move as above), and with them what has no caller left — `renderFactList`, `renderDetails`, `splitFacts`, `drawnByGallery` and their helpers in `personPage.ts` and `factRow.ts`, the strings `record.names`, `record.events`, `record.details` and `record.info`, and the `.is-detail` and `.gedcom-name*` rules, which `lint` and a search for each confirm; `host.select` and `options.selected` are left, as stated; `notes.ts`, `related.ts` and `otherData.ts` keep serving the event card; in `personPage.ts` and `familyPage.ts` the retelling sections go and the family section, the media and the timeline stay. The event row stays for the family section and the place card, dot for a source included. `renderSourcePage` gains the same `open`, `folded` and `host` a person's page has, for the tree's state.

## Risks / Trade-offs

- [A card dense with facts at a glance becomes a tree of closed nodes] → A closed node shows a one-line summary — an event its date and place, an attribute its value — so the first screen reads as the old card did, and *Open every node* is one press.
- [Lines shown twice: the pointer to a family in the tree and the family section] → Accepted and stated; the tree is the file, the section is the people.
- [A person with several hundred lines draws slowly, and *Open every node* draws them all] → Lazy children; the Playwright spec times the first draw and *Open every node* on a long record, and the number is recorded in the PR.
- [The event rows are removed from a person's and a family's own card, and with them the dot for "cites a source"] → The citation is a row beneath the event, where the file states it, and the event card still shows what an event rests on.
- [`hover: none` is not what Obsidian's mobile app reports in every webview] → The `.is-mobile` class and `pointer: coarse` are used beside it, as the card's touch sizes already do.
- [The unchanged specs that name the old sections] → The deltas modify or remove every requirement the review found; `openspec validate` and the second review look for the rest.

## Migration Plan

None: no setting, no data. Rollback is a revert of the change.

## Editing

Added on 2026-11-11, when the user asked for the tree to write; it was first planned as a change of its own stacked on this one and folded in.

### Context

- The tree (`src/desk/detail/tree.ts`) is drawn from `RecordLine`s of `index.record(xref)`; each line carries its `range`. Its host (`TreeHost`) already has `addableAt`, `choicesAt`, `pointerChoicesAt`, `removableAt`, `removeAt`, `chooseField` and `choosePointer`, answered in `GedcomView` from `src/desk/addableFields.ts` over `this.language.update(this.editor.state.doc)`.
- What writes today: `GedcomView.removeAt` calls `removeStructure(at, this.language.getVersion())` and applies the result with `applyWorkspaceEdit` (one CodeMirror transaction, refused if the version moved), with a `ConfirmModal` when lines go with it.
- What does not: `DeskViews.chooseField` builds an Obsidian `Menu` whose items do `onClick(() => undefined)`; `PointerModal.onChooseItem()` is empty; the tree's dropdown resets itself on `change`; values are read-only text areas (`renderField`).
- The card is redrawn from the text after every change (`editsSettled`, 300 ms debounce, and a redraw when a write is applied); focus is restored by `data-focus-key`; per-record node state lives in the session (`treeSession.ts`).
- The language service (linked from the upstream worktree of lavich/domorium#522) answers, probed on a 7.0 text: `addStructure(at, "SURN", {})` writes an empty `2 SURN` line; `addStructure(at, "DEAT", {})` writes `1 DEAT` with the warning `VAL010`, `{value: "Y"}` writes `1 DEAT Y` clean; a `NOTE` value with a newline is written with `CONT`; refusals come back with codes — `value-not-in-enum`, `payload-datatype` (with a message such as "NOV has 30 days"), `unresolved-pointer`, `reciprocal-pointer-unsupported` for `FAMS`, `cardinality-exceeded`, `stale-document` for a stale version.

### Decisions

**The write logic is pure functions over the service; `GedcomView` is a thin wrapper.** `src/desk/edits.ts` (new) takes a `GedcomLanguageService`, a position, a version and an input, and returns the edit, the refusal or the warnings; `addableFields.ts` keeps answering what may be added. They are unit-tested against the real service. `GedcomView` passes its service, applies the edit with `applyWorkspaceEdit`, and redraws; `PointerModal` and the field menu only call back. The `obsidian` package cannot be imported at runtime in a unit test, which is why nothing that needs testing lives in those wrappers.

**Positions and the version come from the drawing, not from the commit.** When the card is drawn, `GedcomView` updates its service from the editor's text and hands the tree that version with the lines; every write the tree asks for carries the version and the position of the line as drawn. At commit, `GedcomView` updates the service from the current text and calls the operation with the drawn version, so a change made against text that has moved — the card's own write not yet redrawn, a second press, a question left open while the file changed, an edit in Source — is refused by the service as `stale-document`, and the card is redrawn with the typed value kept and a notice. The removal already on the branch reads the version at commit and is changed to the same path. Alternative: read the version at commit. Rejected: the service then always agrees, and an old position lands on whatever line is there now.

**A write the card makes redraws the card at once.** After a successful `applyWorkspaceEdit` that came from the card, `GedcomView` cancels the pending debounced redraw and redraws synchronously, so the next action is made on the new lines. A field remembers the value it last wrote and writes nothing when the draft equals it, so Enter followed by leaving the field is one write.

**A field holds the file's value while it is edited.** The tree draws a value in the reader's words (`valueText`); on focus the field's text becomes the payload as the file writes it (`line.text`: a name with its slashes, `F` for a 5.5.1 sex the service lists no values for), and on blur it reads in the reader's words again. A value the service lists is a dropdown whose options carry the standard's values and show the reader's words, so no translated word is ever written. A multiple enumeration (`RESN`) is an Obsidian `Menu` of checked values written as the standard's comma list.

**What is multi-line is the plugin's list, because the description cannot say.** `describeStructure` reports `NOTE`, `CAUS`, `OCCU` and `GIVN` all as `text`. The text of a `NOTE`, an inline `SNOTE` and a `TEXT` takes Enter as a new line; every other field turns a typed or pasted line break into a space, because the service writes it as `CONT` even under a `DATE`. Both are raised upstream.

**Adding is decided by the field's description.** `none`, and `boolean` for an event, are written at once, the event as `Y` — the input this plugin gives the service, so that an added event says it happened; the service would write `1 DEAT` with a warning. A pointer opens the list first and writes on choice; a pointer with no candidates, and one marked `reciprocal`, is disabled in the menu. `text-or-pointer` (5.5.1 `NOTE`, `SOUR`) is offered twice. Anything else becomes an **unwritten row**, with an empty field for each field the description of the new structure marks required (`describeSchemaPath` on the path of the new field: `ROLE` for `ASSO`, `TYPE` for `EVEN` and `FACT`, `LANG` for `TRAN`), each checked with `validateValue` as it is committed, and written with `addStructure(…, { value | pointer, children })` once all have values; left empty, it is dropped. An unwritten row is kept in the session under the record and the parent's node key together with the parent line's text and range at the time it was made; on a redraw it is shown only if the parent at that key still has that text, otherwise it is dropped, and at commit its position is the parent as drawn with the drawn version (above).

**An emptied field is the service's to judge.** The plugin writes an empty value where the service accepts one and shows the refusal where the standard requires a value (`value-required`). The service rewrites `NAME` when `GIVN` is emptied (` /Curie/`); that is raised upstream, not worked around.

**Paired pointers are not offered.** A field the description marks `reciprocal` (`FAMS`, `FAMC`, `HUSB`, `WIFE`, `CHIL`) has no list on its row and is disabled in the menu, with a line saying the link is changed on the other record.

**Commit before another control acts; a way to cancel on touch.** Every control of the tree commits the focused field's pending value on `pointerdown` before its own action, because a tap on a `div` role button does not move the focus on iOS. A blur during the card's own teardown is ignored. On a touch device a small control beside a changed field puts the file's value back, where there is no Escape. Enter while an input method is composing (`isComposing`) does not commit.

**The menus are Obsidian's own; a keyboard-opened menu opens at its control.** The field menu is an Obsidian `Menu`, its items the fields' names in the reader's language; opened with the keyboard it is shown with `showAtPosition` at the control's rectangle, not at the synthetic click's (0, 0). The record list is a `FuzzySuggestModal`. Their keyboard handling is Obsidian's and is checked by hand in the demo vault; the harness tests a stand-in that calls the same callbacks.

**Refusals are shown by code, in the plugin's words.** Keys `edit.refusal.<code>` in both catalogues, with the service's message as the fallback (the service speaks English). Warnings are shown under the field and announced through the card's polite live region.

**Focus after a change.** A written value keeps the focus on its field. An added line puts it on its field or, for a node, on its menu. A removal puts it on the menu of the line the removed line was under, not on a sibling that took the removed line's key.

**Custom lines.** The service does not describe a `_TAG`, but sets its value and removes it: such a line keeps its field and its removal and has no menu.

**No dialect, no editing.** `describeStructure` refusing with `no-dialect` makes the host answer no addable fields, no choices, no removals, read-only fields, and the tree says once why. A record with nothing beneath its opening line shows its root alone, with its menu.

### Risks

- [The change cannot merge before the upstream release] → The whole change waits for that release; built against a local link until then.
- [Pointers the standard pairs cannot be changed] → Said on the row; changing them waits for upstream.
- [An added field lands where the service puts it] → The node is opened and the new row takes the focus, so it is in view.
- [Obsidian's `Menu` and `FuzzySuggestModal` cannot run in the harness] → The callbacks they call are tested through a stand-in; the real menus are checked by hand in the demo vault and on a phone.
- [Upstream gaps: no multi-line marker in the description, a line break accepted under `DATE`, `NAME` rewritten when `GIVN` is emptied] → Raised upstream; the plugin's list of multi-line fields and the space for a line break are recorded here as the only plugin-side rules, to be removed when the description says.

## Implementation

Where the code differs from the plan above, or settled something the plan left open:

- `renderSourcePage` already took `host`; it gains one trailing parameter `options` (`open`, `folded`, `tree`), not three.
- `CardTab.arrivedBy()`, `CardView.session` and `CardView.redraw()` are required members; `GedcomView` answers `arrivedBy()` from the origin of its last `selectRecord`, and every test and the harness that builds a tab or a view gives them.
- The session is `TreeSession` in `src/desk/detail/treeSession.ts`; the tree reads it through the `TreeState` interface, and falls back to an ephemeral state, which redraws the tree itself where the state has no `changed()`. `rememberScroll` creates the memory of a record, so the cards of events, places and media count towards the twenty and have a scroll to return to.
- A note of the tree is keyed `note:<node key>` for the note line itself; a pointer to a shared note draws the note and the lines beneath it with their own counter scoped to the row, so their keys are `note:<node key>.0`, `note:<node key>.1`, and so on. `DetailContext.open` is widened to `{ has(id) }` so that the session can stand for it, and `renderNoteText` takes the key as an optional argument.
- `valueText` and a new `fieldKind` are exported from `lineView.ts`; `renderLine`, `renderLines` and `renderRest` carry the owner of the lines so that `TYPE` is read as the type of a name only under a `NAME`. The no-name placeholder is read in `valueText` for a `NAME` line.
- `NOTE_TAGS` is in `notes.ts` and read by `eventDetails.ts`; `RELATED_TAGS`, `noteLines` and `relatedLines` had no reader left and are gone with `claims.ts`.
- A closed node that points at a record not in the file shows the pointer's *Show in source* in its summary; once open, the pointer's own action is the only one. No row has a *Show in source* of its own, and no row-last-pressed state is kept.
- The header holds one control, the toggle, whose key is `tree:toggle`.
- A closed summary is a flex row of parts; the last part, the place where there is one, is the one the panel cuts with an ellipsis, so the date is not cut before it. The dot counts the `SOUR` lines directly beneath the line.
- On touch, the row is at least 44 pixels tall, the chevron 34 by 44, and a fact's label has a 44-pixel hit area made by a pseudo-element; the toggle takes the app's size for a button of its kind.
- *Open every node* and *Close every node* touch node keys only; what the reader showed of a long note is left as it was.
- The person page's own `drawTree` helper serves the family and the source page; the `FactKey` selection of the heading's *Show in source* is unchanged.
- Timing, 80 events of seven lines (561 rows once open), the harness in headless Chromium: first draw about 30 ms and *Open every node* about 33 ms; the card of `main` draws the same record in 21 to 32 ms (it draws only the compact event rows, no notes and no sources).
- Not checked: Obsidian itself on desktop and on a phone (task 4.2); only the harness was looked at, in both themes at 320 and 390 pixels.
- A record without an identifier cannot be selected, so no card shows one and a card needs no tree for it; the inert label of a fact with no `eventId` is covered on the renderer alone.
- The tree is drawn for person, family and source cards only, and only those take a slot of the twenty and a remembered scroll. Focus is restored by key only while the same record is shown; for another record only the card-level controls (Back, Forward and the toolbar) keep it.
- The header sits in the flow above the first row and is always shown. The arrow is named by its row, with its ordinal where a tag repeats among its siblings (`Name 2`).
- *Open every node* and *Close every node* are one icon button, `gedcom-tree-toggle`, with the `clickable-icon` class and the lucide icons `chevrons-up-down` and `chevrons-down-up` drawn by `setIcon`; its name is the action it will do now and Obsidian's tooltip shows it from `aria-label`. Its focus key is `tree:toggle`; the tags control is unchanged.
- The node header takes Obsidian's file-explorer vocabulary — `tree-item`, `tree-item-self`, `is-clickable`, `mod-collapsible`, `tree-item-icon collapse-icon`, `tree-item-inner`, `tree-item-children` — and its variables (`--nav-item-*`, `--nav-collapse-icon-color`, `--indentation-guide-*`, `--clickable-icon-radius`, `--icon-xs`); the layout is written in `styles.css` on our own selectors and does not rely on the app's rules. The arrow is the app's own `right-triangle` icon (a down-pointing triangle) drawn by `setIcon`; `is-collapsed` is set on the node's `tree-item` wrapper and on the arrow when the node is closed, kept in step on every toggle, redraw and open-all, and the app's rule `.collapse-icon.is-collapsed svg.svg-icon` turns it to point at the reader's end, with `--direction` handling right-to-left. Our CSS sets no size, stroke, rotation or transition for the icon. The harness palette carries a small shim of the app's `.tree-item*` rules. A press on a node's header outside its controls opens or closes it.
- Obsidian's own rules for `tree-item-self` and `collapse-icon` took the padding and the margin of our rows in the app; the layout rules of the tree are therefore written under `.gedcom-tree`, with more specificity than the app's, and a leaf row reserves the same column at its start as a node row has for its arrow, so the labels of one depth start at one place.
- Obsidian's own stylesheet adds a zero-width `::before` to every `tree-item-self`, which became a flex item of the row and took the row's gap before the label of a node and not of a line; our rows set `content: none` on both pseudo-elements, and the harness palette now carries the app's real rules for `tree-item-self`, `tree-item-icon` and `collapse-icon`, so that the specs fail on the old rules. The arrow's column is 24 pixels (30 on touch) and the glyph is followed by about six.
- The arrow follows the explorer's markup: `tree-item` wrapper, `tree-item-self` row, `tree-item-icon collapse-icon` button holding `right-triangle`, `tree-item-inner` label, `tree-item-children`. The row's start padding is `--size-4-6`, the arrow's box starts at `--size-4-6` minus `--size-4-5` and is `--size-4-4` wide, as in the app, so the glyph is followed by about seven pixels; on touch the box is `--size-4-6` wide from the start and 44 pixels tall. The harness palette mirrors the app's `.collapse-icon` rules and `--direction`.
